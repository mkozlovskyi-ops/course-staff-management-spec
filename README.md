# Репо вимог команди (шаблон)

> **Заповнює PM** після створення репо (олівець «Edit this file» праворуч над цим текстом → правки → «Commit
> changes…»):
>
> - Команда: `course-staff-management`
> - Сховище вимог: **docs/**
> - Продукт: [`docs/product.md`](docs/product.md)

Тут PM команди веде **вимоги до продукту** людською мовою за шаблоном. Коду, бази й деплою тут немає, і нічого
встановлювати не треба: усе робиться у вебінтерфейсі GitHub.

Кожен розробник команди робить **власну** реалізацію того самого продукту у своєму репо `<dev>/<team-slug>` (з
[шаблону проєкту](https://github.com/koldovsky/2026-quitcode-06-project-template)). Вимоги звідси він забирає
командою агента `/requirements-sync` і сам перекладає їх у технічну специфікацію (OpenSpec) — це робота
розробника, не PM. Питання до вимог розробники ставлять тут, в issues.

```text
 PM:          <pm>/<team-slug>-spec
              issue «Продукт» + issues «Вимога»    — або —    docs/product.md + docs/requirements/*.md
                   ▲                                   │
                   │ issues «Питання до вимог»         │ /requirements-sync (агент розробника)
                   │                                   ▼
 Розробники:  <dev>/<team-slug>   у кожного своє репо, своя специфікація і своя реалізація
```

Три правила:

1. **Чинні вимоги — це текст** відкритих issues «Продукт» і «Вимога» (або файли `docs/` у гілці `main`). Не
   коментарі, не чат, не усні домовленості: розробники отримують лише цей текст.
2. **Будь-яка зміна** — правка тексту + рядок у «Журнал змін» + повідомлення «вимоги оновлено» в чаті команди.
3. **Питання — issues «Питання до вимог» у цьому репо.** Відповідь — там само, її бачить уся команда.

Покрокова інструкція з поясненнями й доказами для оцінювання — у
[`docs/walkthrough-pm.md`](https://github.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/blob/main/docs/walkthrough-pm.md)
репо домашки. Тут — короткий шлях. Назви кнопок — з англійського інтерфейсу GitHub; точну назву перевірте в
інтерфейсі.

## Шлях PM

### 1. Створіть репо (день 0)

1. Відкрийте <https://github.com/koldovsky/2026-quitcode-06-spec-template> → зелена кнопка **Use this template** →
   **Create a new repository**.
2. **Owner** — ваш особистий акаунт; **Repository name** — `<team-slug>-spec` (наприклад, `leave-portal-spec`);
   **Public** — обов'язково й назавжди: розробники забирають вимоги без прав доступу, а форму питань відкриває
   будь-хто з акаунтом GitHub.
3. **Create repository**.
4. Перевірте, що є вкладка **Issues** (у нового репо вона увімкнена; якщо ні — **Settings** → **General** →
   **Features** → **Issues**).

### 2. Мітки (день 0)

Форми issues ставлять мітку, лише якщо вона вже є в репо, а розробники знаходять вимоги саме за мітками. «Use this
template» мітки не копіює.

1. **Issues** → **Labels** → **New label**.
2. Назва `product` → **Create label**. Так само створіть `requirement`.
3. Мітка `question` зазвичай уже є серед стандартних міток GitHub. Якщо її немає — створіть так само.

Назви міток — саме такі, латиницею й малими літерами.

### 3. Оберіть, де писати вимоги, і запишіть вибір (день 0)

| | **issues** (за замовчуванням) | **docs/** (за бажанням) |
|---|---|---|
| Продукт | одне issue «Продукт» | файл `docs/product.md` |
| Вимога | по issue «Вимога» на зріз чи фічу | по файлу `docs/requirements/<NN>-<slug>.md` |
| Як заповнювати | форма з полями | копія `docs/requirements/_template.md` |
| Зміна | редагування issue + коментар «Зміна: …» | редагування файлу + повідомлення коміту «Зміна: …» |
| Кому зручніше | тим, хто звик до тікетів | тим, хто звик до документів |

Розділи вимоги однакові в обох варіантах, і розробники отримують однаковий результат. Оберіть один варіант для
всього — продукту й усіх вимог. Питання розробників в обох варіантах приходять в issues.

Запишіть вибір угорі цього README: олівець **Edit this file** → у блоці «Заповнює PM» лишіть `issues` або `docs/`,
впишіть слаг команди → **Commit changes…** → **Commit directly to the `main` branch** → **Commit changes**.

### 4. Зустріч команди (дні 0–2)

Ви організовуєте перший раунд питань до брифу: дзвінок на 15–20 хвилин до кінця 15.10. Якщо не вдається зібратися —
асинхронно в чаті команди: діри від розробників — до обіду 16.10. Відповіді — у вимоги, те, що лишилось
невирішеним, — у «Відкриті питання».

### 5. Продукт (до кінця 16.10)

- **issues:** **Issues** → **New issue** → форма **Продукт** → заповніть поля → **Create** (точну назву перевірте в
  інтерфейсі). Одне issue «Продукт» на репо, завжди відкрите: щоб щось змінити — редагуйте його, а не створюйте нове.
- **docs/:** відкрийте `docs/product.md` → олівець **Edit this file** → заповніть розділи → **Commit changes…** →
  **Commit directly to the `main` branch** → **Commit changes**.

Розділи: **Бачення** · **Користувачі й ролі** · **Матриця прав** (роль × дія) · **Глосарій** · **Roadmap зрізів** ·
**Що поза scope**. Ідентифікатори ролей — латиницею (`member`, `admin`): розробники беруть їх у свої реалізації.

### 6. Вимоги першого зрізу (до кінця 16.10)

- **issues:** **Issues** → **New issue** → форма **Вимога** → назва `Вимога: <що зможе користувач>` → поля →
  **Create**. Одне issue — одна вимога.
- **docs/:** покроково — у [`docs/requirements/README.md`](docs/requirements/README.md): **Add file** →
  **Create new file** → `docs/requirements/01-<slug>.md` → текст із `_template.md` → заповнити → коміт у `main`.

Відкрите issue «Вимога» з міткою `requirement` (чи файл у `docs/requirements/` гілки `main`) розробники заберуть
при наступній синхронізації, тож публікуйте вимогу з готовим текстом. **Чернетка** (наприклад, вимоги наступного
зрізу для бонусу E) має лежати поза знімком розробників:

- **issues:** створіть її через форму **Вимога** з назвою `Чернетка WS7: …` і **одразу після створення** зніміть
  мітку `requirement` (праворуч **Labels** → зніміть позначку). Коли настане час — поверніть мітку й змініть назву
  на `Вимога: …`;
- **docs/:** файл у теці `docs/drafts/`, а не в `docs/requirements/`. Коли настане час — створіть файл у
  `docs/requirements/` з цим текстом, а чернетку видаліть.

Розділи вимоги: **Навіщо** · **Користувачі й ролі** · **Основний сценарій** · **Критерії приймання** · **Поза
межами** · **Припущення** · **Відкриті питання** · **Журнал змін**. Якщо в «Поза межами» чи «Відкриті питання»
нічого — «Немає». «Припущення» не залишайте порожніми: щонайменше часовий пояс, хто створює дані, одиниці й точність
(дати, суми, округлення).

**Критерії приймання (AC)** — головне. Кожен критерій — окремий пункт списку:

```text
- AC-<AREA>-<NN>: Дано … Коли … Тоді …
```

- `AREA` — 2–12 великих **латинських** літер (набирайте на англійській розкладці: кирилична «А» чи «С» виглядає так
  само, але агент розробника такий ID не знайде), `NN` — дві цифри: `AC-RESERVE-01`, `AC-RESERVE-02`.
- Один критерій — **один рядок**: Enter усередині критерію не натискайте, довгий рядок редактор переносить сам.
- Один критерій — одна поведінка, з конкретними числами й текстами повідомлень.
- Хоча б один критерій — про помилку чи відмову (неправильні дані, чужі дані, ліміт).
- Жодних технічних рішень: таблиць, API, кнопок, бібліотек.
- ID **унікальний у всьому репо**: двох однакових ID не може бути навіть у різних вимогах. Найпростіше — своя `AREA`
  для кожної вимоги (`AC-RESERVE-…`, `AC-RETURN-…`); якщо `AREA` спільна — нумерація наскрізна.
- ID назавжди: розробники називають ними свої тести. Змінений критерій зберігає ID; новий — наступний вільний номер;
  прибраний ID більше не використовуйте.

Приклад (з іншої області — міська бібліотека; у вашому редакторі кожен критерій — один довгий рядок):

```text
- AC-RESERVE-01: Дано читач без активних резервувань і книжка з 2 вільними примірниками. Коли читач резервує книжку. Тоді резервування має статус «очікує видачі», вільних примірників стає 1, а резерв діє 3 доби.
- AC-RESERVE-02: Дано читач, у якого вже 5 резервувань зі статусом «очікує видачі». Коли він резервує ще одну книжку. Тоді резервування не створюється, і читач бачить повідомлення «Не більше 5 резервувань одночасно».
```

Повний заповнений приклад вимоги — у [`docs/requirements/README.md`](docs/requirements/README.md#приклад-заповненої-вимоги).

### 7. Самоперевірка за чеклістом (до кінця 16.10)

Пройдіть кожну вимогу за [`docs/checklist.md`](docs/checklist.md): 20 пунктів якості й 11 категорій
неоднозначностей. Там же — готовий промпт для будь-якого AI-чату. Результат запишіть:

- **issues:** коментар у issue «Вимога»: `Перевірено за чеклістом: …` (що «так», що виправили, що лишили);
- **docs/:** рядок у «Журнал змін» файлу: `- 2026-10-16 — Перевірено за чеклістом: …`.

### 8. «Вимоги оновлено» в чаті команди (до кінця 16.10)

Напишіть у чат команди, наприклад: «Вимоги оновлено 16.10: продукт і 2 вимоги першого зрізу, AC-RESERVE-01…07.
Посилання: …». Без цього повідомлення розробники не знають, що пора запускати `/requirements-sync`.

### 9. Питання й уточнення (до кінця 18.10)

Розробники створюють issues **«Питання до вимог»** (мітка `question`): посилання на вимогу, AC, питання, варіанти
A/B/C, рекомендований варіант і вплив.

1. Відповідайте **коментарем у питанні**: який варіант і чому. Можна свій варіант.
2. Якщо відповідь змінює поведінку — змініть вимогу (розділ нижче) і в «Журнал змін» дайте посилання на питання.
3. Закрийте питання: **Close issue** (точну назву перевірте в інтерфейсі). Дублікат закрийте коментарем «Дубль #N —
   відповідь там».
4. Після змін — «вимоги оновлено» в чаті з переліком змінених і нових AC.

Якщо в питання не стала мітка `question` (наприклад, його створили без форми), поставте її самі: праворуч
**Labels** → `question`.

## Як змінити вимогу

**issues:**

1. Відкрийте issue «Вимога» → на першому дописі меню **…** → **Edit**.
2. Змініть текст у потрібному розділі. Заголовки розділів (`### Навіщо`, `### Критерії приймання` тощо) не
   видаляйте й не перейменовуйте.
3. Допишіть рядок у **Журнал змін**:
   `- 2026-10-18 — AC-RESERVE-02: прострочені резервування не рахуються в ліміт — питання <адреса питання>`.
   Адресу питання скопіюйте з адресного рядка: тут вона показується як `#7`, а в копії розробника лишається робочим
   посиланням.
4. **Save** або **Update comment**, залежно від версії інтерфейсу (точну назву перевірте в інтерфейсі).
5. Додайте **новий коментар** `Зміна: AC-RESERVE-02 — … (питання #7)`: розробники, які стежать за issue, отримають
   сповіщення.

**docs/:** відкрийте файл → олівець **Edit this file** → правка + рядок у «Журнал змін» → **Commit changes…** → у
полі повідомлення коміту — `Зміна: AC-RESERVE-02 — <адреса питання>` → **Commit directly to the `main` branch** →
**Commit changes**.

В обох варіантах: змінений критерій зберігає свій ID; новий отримує наступний вільний номер; прибраний — видаліть з
«Критерії приймання» і запишіть у журнал, чому; цей ID більше не використовуйте. Потім — «вимоги оновлено» в чаті.

**Скасувати вимогу цілком** (рідко; спершу обговоріть з командою):

- **issues:** коментар `Скасовано: <причина>` → **Close issue**. Розробники побачать при синхронізації, що вимогу
  прибрано.
- **docs/:** відкрийте файл → меню **…** → **Delete file** → **Commit changes…** (точну назву перевірте в
  інтерфейсі).

AC ID скасованої вимоги більше не використовуйте. Потім — «вимоги оновлено» в чаті з причиною.

## Як розробники забирають вимоги

У своєму репо розробник запускає в Claude Code чи Cursor команду `/requirements-sync` (перший раз — з адресою
вашого репо: `/requirements-sync <pm>/<team-slug>-spec`). Команда:

- шукає тут **відкриті** issues з міткою `requirement`. Якщо вони є — бере текст кожного такого issue і текст
  відкритого issue з міткою `product`;
- якщо таких issues немає — бере з гілки `main` файли `docs/product.md` і `docs/requirements/*.md`, крім
  `_template.md` і `README.md`;
- кладе знімок у теку `requirements/` свого репо і показує, які вимоги й критерії додано, змінено чи прибрано (за
  AC ID) і які рядки з'явились у «Журнал змін»;
- далі розробник перекладає ваші вимоги у свою специфікацію OpenSpec, зберігаючи ваші AC ID, і реалізує їх.

Що з цього випливає для вас:

- **Беруть лише текст.** Коментарі в issues до розробників не доходять — усе важливе має бути в тексті issue чи файлу.
- **Не закривайте issues «Вимога» і «Продукт»**, поки вимога чинна: закрите issue розробники не отримають.
  Закривати можна лише питання.
- **Одне issue «Продукт».** Друге відкрите issue «Продукт» заплутає синхронізацію — редагуйте наявне.
- **Мітки обов'язкові.** Issue «Вимога» без мітки `requirement` розробники не побачать. Якщо issue «Вимога» чи
  «Продукт» створив не PM — закрийте його.
- **У варіанті `docs/` не створюйте issues «Вимога»:** одне відкрите issue з міткою `requirement` перемикає
  синхронізацію на issues, і ваші файли буде проігноровано.
- **Репо публічне, гілка — `main`.** Приватне репо чи інша назва гілки — і `/requirements-sync` перестане працювати.
- **Після змін — «вимоги оновлено» в чаті.**

## Чого не робити

- Не пишіть тут код, технічні рішення чи специфікацію OpenSpec: це робота розробників у їхніх репо.
- Не пишіть вимоги в коментарях і в чаті — лише в тексті issue чи файлу.
- Не перенумеровуйте, не використовуйте повторно й не дублюйте AC ID у різних вимогах.
- Не змінюйте вимогу без рядка в «Журнал змін».
- Не закривайте issues «Вимога» і «Продукт», поки вони чинні; не видаляйте issues питань.
- Не змішуйте варіанти: або issues, або `docs/` для всього.
- Не перейменовуйте розділи вимоги й поля форм: за ними розробники порівнюють версії.
- Не робіть репо приватним і не перейменовуйте гілку `main`.

## Анонімізація

Репо публічне, а ваші тексти потрапляють у публічні репо всіх розробників і в AI-чати.

- Жодних справжніх назв клієнта, імен людей, адрес, сум і внутрішніх документів — ні в issues, ні у файлах, ні в
  коментарях. Пишіть ролями й узагальнено: «школа», «агенція», «практика»; приклади — вигадані
  (`teacher1@example.test`).
- GitHub зберігає історію редагувань issues і коментарів, і її бачать усі. Якщо справжня назва потрапила в текст,
  виправлення її не прибирає: видаліть стару версію з історії (напис **edited** над дописом → оберіть версію →
  **Delete revision from history**; точну назву перевірте в інтерфейсі) або напишіть викладачу. У варіанті `docs/`
  стара версія лишається в історії комітів — напишіть викладачу.
- Список справжніх назв, яких не має бути в текстах, надішліть розробникам **особистим повідомленням**: у своїх
  репо вони додають його в локальну перевірку, яка ловить такі назви у ваших вимогах.

## Що в цьому репо

| Файл | Для чого |
|---|---|
| `.github/ISSUE_TEMPLATE/product.yml` | форма «Продукт» (мітка `product`) — варіант issues |
| `.github/ISSUE_TEMPLATE/requirement.yml` | форма «Вимога» (мітка `requirement`) — варіант issues |
| `.github/ISSUE_TEMPLATE/question.yml` | форма «Питання до вимог» (мітка `question`) — для розробників, в обох варіантах |
| `.github/ISSUE_TEMPLATE/config.yml` | лише ці три форми, без порожніх issues |
| `docs/product.md` | продукт — варіант `docs/` |
| `docs/requirements/` | вимоги файлами — варіант `docs/`: `_template.md` (шаблон), `README.md` (інструкція й приклад) |
| `docs/checklist.md` | чекліст якості, 11 категорій неоднозначностей, промпт для AI-чату |
| `AGENTS.md` | коротка підказка для AI-асистента, якщо ви працюєте з ним у цьому репо |

Форма питань для розробників: `https://github.com/<pm>/<team-slug>-spec/issues/new?template=question.yml`; усі
форми — `https://github.com/<pm>/<team-slug>-spec/issues/new/choose`.

## Оновлення шаблону

Якщо викладач оголосить у чаті курсу виправлення шаблону, він назве файл, який треба замінити. Відкрийте цей файл у
своєму репо → олівець **Edit this file** → вставте новий текст → **Commit changes…** → **Commit directly to the
`main` branch** → **Commit changes**. Ваші вимоги це не змінює.
